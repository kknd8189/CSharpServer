# 부하 테스트 — 접속 수용 한계와 게임 로직 처리 한계

> **TL;DR** — 서버의 한계는 하나가 아니라 **성격이 다른 두 개의 지표**다.
>
> | 지표 | 무엇이 막히나 | 결과 |
> |---|---|---|
> | **접속 수용** | 신규 접속이 거부됨 | 500 → **1100+** (ThreadPool starvation 해소) |
> | **게임 로직 처리** | 30Hz 틱 예산 초과 | **700 CCU** (틱 p99 33.9ms, 예산 초과 0.9%) |
>
> **단, 700 은 무조건적인 숫자가 아니다.** 서버는 접속 시 맵 전역에 균등 랜덤 스폰하는데
> 실제 유저는 마을·보스에 뭉친다. 같은 700 명을 뭉치게 하자 **틱 p99 가 34 → 245ms** 로 뛰었다.
> 밀집 상태의 실질 한계는 **250~300 CCU** 다 — 10장.
>
> 교훈이 세 번 나왔다.
>
> 1. **가설(MariaDB `max_connections`)이 틀렸고, 실측으로 진짜 원인(.NET ThreadPool + 동기 EF)에 도달했다** — 2~5장
> 2. **틱 최댓값으로 한계를 판정하면 안 된다.** 히스토그램 p99 로 바꾸자 판정이 달라졌고,
>    그 과정에서 부하 클라이언트의 결함과 시야 컬링 버그를 찾아 **p99 를 61% 개선**했다 — 6~9장
> 3. **내 숫자의 전제를 스스로 무너뜨려봤다.** 부하의 공간 분포를 바꾸자 같은 700 이
>    2.5 배 이상 나쁜 숫자가 됐다 — 10장

## 3. 가설과 실측 — 병목 분석

### 3.1 첫 가설: MariaDB `max_connections=151`

부하 클라이언트 1명당 사용하는 DB 연결을 추정해보면:
- AccountServer 측: AccountDB + SharedDB 각 1개
- GameServer 측: GameDB 1개 (Login, EnterGame 핸들러)
- 동시 ramp-up 시 순간 동시 연결 ~3-5개/명

500명 × 3-5 = 1500~2500 conn → MariaDB 기본 한계 151 명백히 초과.
당시엔 이 가설이 가장 강력해 보였다.

### 3.2 실측

`max_connections=1000`으로 올린 뒤 **1000 CCU 부하 재현 후** 확인:

```sql
mysql> SHOW STATUS LIKE 'Max_used_connections';
+----------------------+-------+
| Variable_name        | Value |
+----------------------+-------+
| Max_used_connections | 146   |   -- 1000 한계의 14.6%
+----------------------+-------+
```

**`max_connections`은 진짜 병목이 아니었다.**
EF Core가 DbContext 단위로 connection을 짧게 점유하고 풀로 반환하기 때문에 동시 1000세션이라도 실제 동시 연결은 146개로 수렴.

### 3.3 진짜 원인

코드 베이스를 다시 훑어 두 가지 문제를 발견:

**(1) ThreadPool 최소 워커 미설정** — `Program.cs` / `Startup.cs` 모두 `ThreadPool.SetMinThreads()` 호출 없음. 기본값은 CPU 코어 수(예: 8). 동시 spawn 시 워커 풀이 천천히 (~500ms / 1개) 증가하면서 패킷 처리 콜백이 지연 → **신규 SYN 처리 누락**.

**(2) `HandleLoginAsync`의 EF Core 동기 호출** — `ClientSession_PreGame.cs`에서 `.FirstOrDefault()`가 동기로 사용됨. `await ...Async()` 없이 IOCP 워커가 DB I/O 대기 동안 블로킹 → ThreadPool starvation 가속화.

```csharp
// Before
AccountDb findAccount = db.Accounts
    .Include(a => a.Players)
    .Where(a => a.AccountDbId == loginPacket.AccountID).FirstOrDefault();   // 동기 ❌

// After
AccountDb findAccount = await db.Accounts
    .Include(a => a.Players)
    .Where(a => a.AccountDbId == loginPacket.AccountID).FirstOrDefaultAsync();  // 비동기 ✅
```

## 6. 게임 로직 처리 한계 — 판정 기준을 바꾸다

접속이 뚫린 뒤에도 "그래서 몇 명까지 **제대로 돌아가나**" 는 답하지 못하고 있었다.
5장까지의 근거는 `TickMax`(5초 윈도우의 최댓값) 하나였는데, 이 지표로는 판정이 흔들린다.

### 6.1 세 가지 기준이 서로 다른 답을 냈다

| 판정 기준 | 답 | 문제 |
|---|---|---|
| 틱 **최댓값** > 33ms | 400 CCU | **과도하게 보수적** — 5초에 149틱 중 1틱만 튀어도 걸린다 |
| **지속 Hz** < 29 | 700 CCU | **과도하게 관대** — 그 구간에서 이미 틱의 19% 가 예산 초과인데도 Hz 는 멀쩡해 보인다 |
| **p99 · 예산 초과율** | **500 CCU** | 분포를 보므로 둘 다 아니다 |

Hz 가 관대한 이유가 흥미롭다. 30Hz 루프는 예산을 넘기면 sleep 을 생략하고 따라잡는다(catch-up).
그래서 **틱의 19% 가 예산을 넘겨도 실측 Hz 는 27.9 로 유지**된다. 겉보기엔 멀쩡한데
다섯 틱 중 하나가 프레임을 밀고 있는 상태다. 히스토그램이 없으면 볼 수 없다.

→ 이 시점에 메트릭을 Prometheus 히스토그램으로 옮겼다. [monitoring.md](monitoring.md) 참고.

```promql
# 예산을 넘긴 틱의 비율 — 이 값이 유의미해지는 CCU 가 실질적 수용 한계
1 - (
  sum(rate(game_tick_duration_seconds_bucket{le="0.0333"}[1m]))
  / sum(rate(game_tick_duration_seconds_count[1m]))
)
```

### 6.2 측정 도구 자체가 고장나 있었다

기준을 바꾸고 재보니 숫자가 이상해서 파고들었더니 **DummyClient 에 버그가 두 개** 있었다.

| 버그 | 증상 |
|---|---|
| **이동 축이 틀렸다** — `Up/Down` 으로 `PosY` 를 움직였는데 이 맵은 단일 Y 평면(`MaxY = MinY`) | 서버 `CanGo` 가 **100% 거부**. 방향 4개 중 2개가 y 였으니 **이동 패킷의 절반이 폐기** |
| **서버 보정을 무시** — `S_MoveHandler` 가 빈 껍데기 | 거부될 때마다 클라 좌표만 앞서 나가 격차 누적 → 정상 더미 292 세션이 텔레포트 어뷰저로 킥 |

고친 뒤 **같은 CCU 에서 송신 처리량이 최대 3.9× 증가**했다.
즉 그 이전의 모든 측정은 절반도 안 되는 부하로 잰 것이었다.

## 7. 병목 특정 — 브로드캐스트 팬아웃

정상화된 부하로 재보니 병목이 선명해졌다.

```
900 CCU:  수신 3,062/s  →  송신 42,606/s     (14.6배)
          명당 3.4 패킷      명당 47 패킷
```

수신은 CCU 에 선형인데 송신만 가파르게 증가한다.
비용이 접속자 **수**가 아니라 **시야 안 접속자 쌍**에 비례한다는 신호 — 브로드캐스트 팬아웃이다.

파고들었더니 성능 튜닝 이전에 **버그**였다.

### 7.1 시야 컬링 축이 틀렸다

```csharp
int dx = player.CellPos.x - cellPos.x;
int dy = player.CellPos.y - cellPos.y;   // 단일 Y 평면 → 항상 0, 아무것도 못 거른다
if (Math.Abs(dx) > VisionCells) continue;
if (Math.Abs(dy) > VisionCells) continue;
// z 는 아예 검사하지 않는다
```

존이 `ZoneCells`(10) 단위라 인접 존을 훑으면 z 로 최대 20 셀이 포함된다.

```
의도한 시야:  11 × 11 = 121 셀
실제 전송:    11 × 20 ≈ 220 셀      → 약 1.8배 과다 전송
```

같은 버그가 `Broadcast` 와 `VisionCube` 양쪽에 복사돼 있었다. `GameRoom.IsInVision` 으로 통일.

### 7.2 핫패스 할당

`Broadcast` 는 이동 1건마다 도는 최핫패스인데 호출마다
`GetAdjacentZones` 의 `HashSet`+`List`, `SelectMany` 의 이터레이터/클로저를 할당했다.
존 인덱스를 직접 순회하도록 펼쳐 **할당 0** 으로 만들었다.

### 7.3 A\* — 확장 여지의 비용

```csharp
int[] _deltaY = { 0, 0, 1, -1, 0, 0 };   // 6방향 중 2개가 y → 매번 CanGo 에서 탈락
```

이건 버그가 아니라 **3D 맵을 대비해 의도적으로 넣어둔 확장 여지**였다.
다만 현재 데이터가 단일 평면이라 **노드당 확장의 1/3 이 매번 버려지고 있었고**,
`FindPath` 는 추적 중인 몬스터가 200ms 마다 호출하는 핫패스다.

지우는 대신 `SizeY > 1` 일 때만 6방향을 쓰도록 조건을 달았다.
맵 데이터에 층이 생기면 코드 수정 없이 자동으로 6방향으로 돌아간다 —
**확장 여지는 남기고 현재 비용만 제거**.

> 실제로 다층 맵을 넣을 때는 `±1 y 이웃` 자체를 다시 봐야 한다.
> "위로 한 칸 날아오른다" 는 대부분의 게임에서 유효한 이동이 아니다.
> 층 사이는 계단·사다리 같은 **명시적 연결 노드**로만 이어지는 게 맞다.
> 시야도 y 범위 검사가 아니라 "같은 층인가" 검사가 맞다.

한편 몬스터의 축 정렬 판정(`dir.x == 0 || dir.y == 0`)은 **진짜 버그**였다.
`dir.y` 가 항상 0 이라 조건이 무조건 참이 되어 정렬 검사가 무력화돼 있었다.

## 8. 개선 결과

동일 환경(다른 앱 종료), 200 → 1100 CCU 램프업, 75초 간격.

| CCU | p99 (before) | **p99 (after)** | 개선 | 예산 초과율 (after) |
|---:|---:|---:|---:|---:|
| 500 | 33.0 ms | **20.4 ms** | −38% | 0.00% |
| 600 | 47.9 ms | **24.3 ms** | −49% | 0.10% |
| **700** | 86.4 ms | **33.9 ms** | **−61%** | **0.90%** |
| 800 | 176.1 ms | **47.6 ms** | −73% | 6.58% |
| 900 | 288.2 ms | **72.0 ms** | **−75%** | 18.58% |
| 1000 | (붕괴) | **98.0 ms** | — | 40.27% |
| 1100 | — | **225.9 ms** | — | 62.50% |

**한계: 700 CCU** (p99 33.9ms 로 예산 33ms 를 아슬아슬하게 넘고, 예산 초과 0.90%).
600 CCU 는 완전 안전 구간(p99 24.3ms, 초과 0.10%).

### 연쇄 붕괴가 사라졌다

가장 중요한 변화는 수치가 아니다.

```
before:  999 CCU 에서 80 으로 급락    PingTimeout 715, Kicked 205
after:   1100 CCU 까지 유지          PingTimeout 0,   Kicked 0   (전원 정상 종료)
```

이전에는 게임 스레드가 30초 넘게 막혀 세션 715개가 강제 종료됐다.
지금은 **틱이 예산을 넘어도 연결은 유지된다** — 성능이 떨어져도 우아하게 degrade 하지, 무너지지 않는다.

## 9. 측정 환경이 결과를 2~3배 흔든다

같은 코드를 다른 환경에서 재면 이렇게 갈린다.

| CCU | 최적화 전<br>(조용) | 최적화 전<br>(3코어 점유 중) | 최적화 후<br>(3코어 점유 중) | 최적화 후<br>(조용) |
|---:|---:|---:|---:|---:|
| 500 | 33.0 ms | 53.5 ms | 36.4 ms | **20.4 ms** |
| 700 | 86.4 ms | 235.5 ms | 92.2 ms | **33.9 ms** |
| 900 | 288.2 ms | 997.4 ms | 246.2 ms | **72.0 ms** |

**최적화 전 조용한 환경이 최적화 후 시끄러운 환경보다 낫다.**
즉 환경 노이즈가 최적화 효과보다 컸다. 다른 앱(3코어 점유)을 끄기 전에는
개선을 측정할 수조차 없었다.

> **부하 테스트를 인용할 때 반드시 함께 말해야 하는 조건**
> - 클라이언트와 서버가 **같은 PC**에서 구동 (서버 단독이면 한계치가 더 높다 → **하한선**으로 읽어야 한다)
> - 더미가 실제 유저보다 공격적 (200~500ms 이동, 1~3초 스킬을 쉬지 않고)
> - Docker Desktop(WSL2) 오버헤드
> - **단일 존** 기준. 존이 분산되면 결과가 달라진다
> - 게임 로직이 **단일 스레드**라 12코어 중 1개만 사용
> - **부하가 맵 전역에 균등 분포** — 실제 유저처럼 뭉치면 250~300 CCU 로 떨어진다(10장)

## 10. 밀집 시나리오 — 같은 700 명, 분포만 바꾸면

### 왜 재야 했나

서버는 접속 시 맵 전역(111×111 = 12,321칸)에 **균등 랜덤 스폰**한다(`GameRoom.EnterGame`).
그래서 700 CCU 라도 시야(11×11 = 121칸) 안에는 평균 **6.2 명**뿐이다.

그런데 실제 유저는 마을·보스·사냥터 목에 뭉친다.
이 서버는 **브로드캐스트가 틱 시간의 64%** 를 먹으므로, 팬아웃을 좌우하는 밀집도가
사실상 부하의 전부다. 즉 **기존 700 은 팬아웃이 가장 가벼운 조건에서 잰 숫자**였다.

### 어떻게 쟀나 — 한 변수만 바꾼다

DummyClient 에 `cluster` 명령을 넣었다(`LoadProfile` + `ServerSession.PickDir`).
**서버는 건드리지 않았다.** 더미가 목표 지점으로 걸어가 그 반경 안에서 랜덤 워크할 뿐,
이동 패킷의 전송률·간격·검증 통과 여부는 그대로다. 바뀌는 건 **방향뿐**이다.

```
cluster on 45 45 30    → 중심 (45,45) 반경 30 으로 집결
cluster off            → 맵 전역 랜덤 워크로 복귀
```

재접속 없이 토글되므로 **같은 세션 집합**으로 A/B 를 잰다.
세션을 다시 만들면 스폰 위치·계정·접속 순서가 달라져 교란이 생긴다.

관측을 위해 서버에 메트릭 두 개를 추가했다.

| 메트릭 | 왜 필요했나 |
|---|---|
| `game_broadcast_recipients` | 브로드캐스트 비용은 **호출 수 × 팬아웃**이다. 소요 시간만 보면 둘 중 어느 쪽이 늘었는지 구분되지 않는다 |
| `game_move_blocked_total{reason}` | 지형/점유 거부는 어뷰징이 아니라 카운터를 안 올렸다 → 지표에 흔적이 없었다. 아래 ③ 을 해석하려면 반드시 필요하다 |

> 팬아웃은 **수신자 루프 안이 아니라 Broadcast 호출당 1 회만** 관측한다.
> 예전에 루프 안에서 재다가 초당 2만 회 측정이 되어 **측정 행위가 재려던 대상을 왜곡**한 적이 있다.

### 결과 (700 CCU 고정, 분포만 변경)

| | ① 흩어짐 | ② 밀집 A | ③ 밀집 B | ⑤ 복귀 |
|---|---:|---:|---:|---:|
| 팬아웃 p50 | **6.2** | 14.3 | **21.7** | 6.5 |
| 팬아웃 p99 | 19.1 | 39.0 | 75.1 | 19.1 |
| 초당 송신 건수 | **19,400** | 37,300 | **50,000** | 19,800 |
| 브로드캐스트 호출/s | 2,880 | 2,600 | 2,460 | 2,875 |
| 이동 거부 `occupied`/s | 184 | 350 | 560 | 189 |
| 이동 거부 `terrain`/s | 17 | 0.0 | 0.0 | 12 |
| 틱 p50 | 12 ms | 24 ms | **45 ms** | 11 ms |
| **틱 p99** | **34 ms** | **96 ms** | **245 ms** | 33 ms |

**⑤ 가 ① 로 돌아온 것이 이 측정의 신뢰도를 담보한다.**
팬아웃 6.2 → 6.5, 송신 19,400 → 19,800, 틱 p99 34 → 33ms.
환경이 드리프트한 게 아니라 밀집도 효과라고 말할 수 있는 유일한 근거다.
(이 프로젝트는 환경 노이즈가 결과를 2~3배 흔든다 — 9장)

### 발견 ① 밀집 시 700 은 예산을 완전히 놓친다

밀집 B 에서 **틱 p50 이 45ms** 다. 꼬리가 아니라 **중앙값이** 33ms 예산을 넘었다.
30Hz 를 아예 유지하지 못하는 상태다.

역산하면 밀집 상태의 실질 한계는 **250~300 CCU**.
같은 서버, 같은 패킷 전송률인데 **분포만 바꿔서 2.5 배 차이**가 난다.

> "이 서버는 700 CCU 를 받는다" 는 **조건부 문장**이었다는 게 숫자로 증명됐다.

### 발견 ② 부하 2.6 배 → 지연 7.2 배 (초선형)

```
초당 송신 건수  19,400 → 50,000   (2.6배)
틱 p99          34ms   → 245ms    (7.2배)
```

측정 중 실수로 1400 CCU 가 됐을 때도 같은 패턴이었다 —
부하 2.2 배(송신 18,800 → 40,900)에 **p99 는 30 배**(33ms → 1,000ms).
그때 **틱 p50 은 11 → 14ms 로 멀쩡**했다. 평균만 봤다면 아무 문제 없어 보였을 상황이다.

브로드캐스트 부하는 선형으로 늘어나는데 지연은 절벽처럼 꺾인다.

### 발견 ③ 너무 붐비면 서버가 오히려 한가해진다

```
브로드캐스트 호출/s   2,880 → 2,600 → 2,460   (-15%)
이동 거부 occupied/s    184 →   350 →   560   (+204%)
```

`Map.CanGo` 는 한 칸에 한 오브젝트만 허용한다. 밀집도가 오르면 옆 칸이 차 있어
**이동이 거부되고, 거부된 이동은 브로드캐스트를 만들지 않는다**.
그래서 팬아웃 부하는 밀도에 대해 단조 증가가 아니라 **정점을 찍고 꺾인다**.

실무로 옮기면 이런 뜻이다 — **사람이 너무 많으면 아무도 못 움직여서 서버 지표는 좋아 보인다.**
유저 경험은 최악인데 대시보드는 멀쩡한 구간이 존재한다.
`game_move_blocked_total` 이 없었으면 "브로드캐스트가 줄었다"를 보고도
밀집이 안 된 건지 밀집돼서 못 움직이는 건지 구분할 수 없었다.

> 부수 확인: `terrain` 거부가 밀집 중 **정확히 0** 이 됐다.
> 더미가 전부 벽 없는 중앙부로 이동했다는 증거다.

### 한계 — 이 측정도 완전하지 않다

- 팬아웃 평균에 **몬스터 브로드캐스트가 섞여 있다.** 몬스터는 맵 전역에 흩어져 있어
  수신자가 0 에 가까운데 같이 평균에 들어간다. 반경 30 에서 이론값 22.7 대비 14.3 이 나온 이유로 보인다.
  플레이어 이동만 떼면 밀집 B 에서 약 32 로 추정된다. `Broadcast` 에 `source` 라벨이 필요하다.
- **밀도 상한은 1.0/칸**이다(한 칸 한 명). 700 명이면 반경 13 이 물리적 하한이라
  그보다 더 뭉치게 할 수 없다. 진짜 마을 밀집을 재려면 인원을 줄여야 한다.

## 11. 부하 테스트 도구가 만든 유령 세션

밀집 측정 도중 이상한 상태를 만났다. **더미 100 개가 접속했는데 부하가 0 이었다.**

```
로그인            100 건 성공
세션 연결         100 개
이동 패킷              0
브로드캐스트           0
서버 로그          아무 흔적 없음
```

### 처음 가설은 틀렸다

직전에 700 개가 일괄 종료됐기 때문에 **churn 이 서버 상태를 깨뜨렸다**고 봤다.
재현을 시도했다 — 300 접속 → 일괄 종료 → 즉시 100 접속.

```
3단계에서 브로드캐스트 48,377 건 증가 → 정상 동작
```

**재현 실패였고, 그게 단서였다.** 종료가 원인이 아니라면 접속하는 쪽에 문제가 있다.

### DB 에 답이 있었다

```
Player_0001 → AccountDbId 6     ← 1 번 계정 소유가 아니다
Player_0002 → AccountDbId 33
Player_0050 → AccountDbId 29

계정 1,120 개 중 캐릭터 없는 계정 101 개
```

**이름과 계정이 무작위로 어긋나 있었다.**

더미는 캐릭터를 `Player_{DummyId:0000}` 로 만드는데, `DummyId` 는
`SessionManager.Generate` 에서 **접속이 완료되는 순서대로** 붙는 번호다.
700 개 접속은 비동기 병렬이라 **완료 순서가 매번 다르다.**

```
1 회차: 계정 A 가 3 번째로 붙음   → DummyId 3   → Player_0003 생성
2 회차: 계정 A 가 512 번째로 붙음 → DummyId 512 → Player_0512 요청
                                                → 이미 계정 B 소유 → 실패
```

즉 **실행할 때마다 이름-계정 매핑이 뒤섞이고**, 어긋난 계정은 캐릭터 생성에 실패한다.

### 진짜 문제는 실패가 조용했다는 것

```csharp
// 서버                                  // 더미
Send(new S_CreatePlayer());               if (createOkPacket.Player == null)
                                          {
                                              // 생성 실패     ← 본문이 비어 있었다
                                          }
```

`HandleEnterGameAsync` 도 마찬가지로 조건 두 개를 로그 없이 `return` 하고 있었다.
결과는 **접속은 됐는데 게임엔 없는 유령 세션** — 이동도, 부하도, 로그도 없다.

### 부하 테스트에 의미하는 것

> **"접속 700" 이 "부하 700" 이 아닐 수 있다.**

유령 세션은 소켓만 차지하고 패킷을 보내지 않으므로 **측정값을 조용히 낮춘다.**
이전에 부하 클라이언트가 이동의 절반을 버리고 있던 걸 발견한 적이 있는데(7장),
같은 종류의 함정이 다른 계층에서 또 나온 것이다.

**측정 도구는 서버만큼 자주 의심해야 한다.**

### 수정

| | 내용 |
|---|---|
| 관측 | 진입·생성 실패 5 개 경로에 `CoreLogger.Warn` + 클라에 실패 응답. **조용한 실패 경로 제거** |
| 이름 | 더미 캐릭터 이름을 `Player_{AccountId}` 로 변경 — 서버 발급 전역 고유값이라 재실행·다중 프로세스 어디서도 안 겹친다 |
| 클라 | 생성 실패·진입 거부 시 콘솔에 출력. "이 더미는 부하를 만들지 않습니다" |

검증(150 접속):

```
캐릭터 없는 계정   101 → 1
이름-계정 일치     100 / 100
더미 실패 메시지   0 건
서버 거부 로그     0 건
```

### 곁다리로 찾은 것 — ObjectManager ID 오버플로

```csharp
// [UNUSED(1)][TYPE(7)][ID(24)]
return ((int)type << 24) | (_counter++);   // 마스크가 없었다
```

`_counter` 가 24 비트를 넘으면 캐리가 TYPE 필드로 올라가 `GetObjectTypeById` 가
엉뚱한 타입을 돌려준다. 그러면 `GameRoom.EnterGame` 의 타입 분기가 통째로 빗나가
**플레이어가 룸에 등록되지 않는다** — 위 증상과 똑같은 모습이 된다.

게다가 카운터를 모든 타입이 공유한다. 발사체가 초당 수백 개 생기는 700 CCU 부하에서는
**약 13 시간이면 소진**된다. 이번 증상의 원인은 아니었지만(가동 20 분),
라이브였다면 하루도 못 버티는 버그다. 24 비트 마스킹 + 순환 시 경고로 고쳤다.

## 13. 어필 포인트

수치 향상보다 **분석 프로세스**가 이 작업의 값어치다.

- ✅ **틀린 가설(`max_connections`)을 인정하고 실측을 따라간 것** — 엔지니어링 판단력
- ✅ **판정 기준 자체를 의심한 것** — 최댓값·처리량·p99 가 각각 다른 답(400/700/500)을 내는 걸 확인하고, 왜 갈리는지 설명한 뒤 근거 있는 기준을 골랐다
- ✅ **측정 도구를 먼저 검증한 것** — 부하 클라이언트가 절반짜리 부하를 만들고 있었다.
  나중에 같은 함정을 다른 계층에서 또 찾았다(유령 세션 — 11장). **틀린 가설을 재현 실패로 기각하고**
  DB 까지 따라가 원인을 특정했다
- ✅ **병목을 수치로 특정하고(송신/수신 14.6배) 실제로 61% 개선한 것**
- ✅ **환경 노이즈가 개선 효과보다 크다는 걸 인지하고 통제한 것**
- ✅ **내 숫자의 전제를 스스로 무너뜨려본 것** — 부하의 공간 분포를 바꾸자 같은 700 이
  2.5 배 이상 나쁜 숫자가 됐다. 700 을 방어하는 대신 **그 숫자가 성립하는 조건**을 명시했다
